Moved out of CLAUDE.md on 2026-11-15. Dated, detailed notes per subsystem (design, invariants, board measurements). Newest work first in each bullet; `grep` for a symbol to find its note.


**Rich text (2026-11-15):**
- `FLAG_RICH_TEXT` (bit 8, was `FLAG_DIRTY_B`), prop `rich_text` (0x38, `caps.rich_text`): labels / buttons read their text as an HTML subset (`rich.rs`, docs `ferrite-lang.md` "Rich text"): `<b>`/`<strong>`, `<i>`/`<em>`, `<u>`, `<font color>` (#RRGGBB, #RGB, names, RGB565 numbers; 8 levels), `<br>`, entities; other tags left out, a `<`/`&` that starts none is text. Parsed while laying out (`rich::Cursor`, a copyable place + open tags): nothing stored, so the scene, commits and `dl_key` (flags + text bytes) see one string as before.
- Bold / italic = font families: V3 header bytes 8..10 = the bold / italic / bold italic variants' font ids (`Font::variant`; bold italic falls back to bold, then italic; none = the font itself), written by `ferrite_build` from the project's font entries (`"bold"`, `"italic"`, `"bold_italic"` = font names). `FontList::find_or_load` loads a font's variants with it (the render side only gets loaded fonts).
- Layout (`render::rich_label`, `Rich`): `Rich::wrap` breaks as `Font::wrap_line` (test `render::rich_tests::plain_text_wraps_the_same_as_rich_text`), lines in the regular font's line height, alignment by the line's width. `label_lines`' callback takes `LabelItem`: `Text` per run of one font + colour (a 120-byte buffer; a full one continues at its pen: same pixels), then `Rule` per underline (after the line's text: an opaque glyph cell drawn later would cover it; y = baseline + max(1, lh/12), max(1, lh/20) thick). Plain labels take the old path unchanged. exynos compositor: runs in their colours, rules as `solid`s; `renderer.rs`' label sprite key hashes the flag.
- Tools (ferrite-ui): `ferrite_rich.py` (Python copy of the parser, Designer preview: runs, variants, colours, underlines; one line per `<br>`, no wrap), Designer `rich_text` box + double-click a font for its variants; `ferrite_build` rejects `rich_text` without `caps.rich_text` and variants on non-V3 fonts.
- Sim (Segoe UI 26 regular/bold/italic/bold italic + a font without variants; wrapping, centred / right-aligned, nesting, entities, `<br>`): one frame in plain / DL verify / areas / play. Board: the same frame (±2 per channel: the BMPs' 565→888 rounding) in render modes 0–3 (`POST /api/rcore?mode=`, the program re-rendering every second). Golden 13/13 default and `--dl`.

**V3 fonts (2026-11-15):**
- V1/V2 font resources store glyph metrics in 7 bytes (offset u16, w/h/advance u8, offsets i8): at 96 DPI they end around 130pt (Ubuntu 130pt: `"` has yOffset −130; a 2bpp ASCII set passes 64 KB of bitmap). V3 (magic `00 03`, 12-byte header with `y_advance` u16 + font_id + bpp + three variant font ids (rich text, below) + 0, 14-byte glyphs: offset u32, w/h/advance u16, offsets i16; bitmap as V1/V2) lifts both. `GfxGlyph` is the wide form for every version (`font::Header::read` tells them apart; a V1 font of 0x0300 glyphs is not taken for V3: V3 needs bpp 1/2 in byte 7 and its tables to fit). `line_height`, `char_width(_cp)` and `draw_char` return u16.
- Tools (ferrite-ui): `caps.font_v3` on `exynos4412-xl` (build-time only, no CAPS bit). `ferrite_build` repacks every font of such a project as V3 (`ferrite_font_converter.to_v3`: same glyphs and bitmap, so the same pixels) and rejects a V3 font for other devices; the Designer generates V3 for them; `ferrite_font_converter.py resource --v3`; the V1/V2 range errors name `--v3`. The converter imports freetype-py only to rasterize (`ferrite_build` uses its `parse_header` / `read_resource`).
- Golden 13/13 default and `--dl` with every example font as V3 (`setup.img` rebuilt: its fonts are V3 now). Test `font::tests::v3_fonts_hold_wide_metrics` (300 px glyph at bitmap offset 70 000, yOffset −200, line height 310). Sim: Ubuntu 130pt Turkish 2bpp (233 KB), 200pt digits, 130pt 1bpp: same frame in plain / `FERRITE_SIM_DL_VERIFY` / areas / play.

**WiFi join with a Zyxel EX3501 (2026-11-15):**
- Symptom: `wifi join ERROR Wpa(RsnMismatch)`, then `Disconnected { event: 6, reason: 15 }` (4-way handshake timeout) on every later try until a restart; a Mi Box failed with the same modem. Cause: the modem (MediaTek, one SSID on 2.4 + 5 GHz, PSK + FT-PSK, MFP capable) sends its RSN element **without** a PMKID list in probe responses (`301e…`) and **with** one in beacons and in message 3 (`302e…0100 <PMKID> 000fac06`), and changes the PMKID over time. The HAL's supplicant compared message 3's element byte for byte with the scan's (whichever frame came first), so a scan that kept the probe response's element failed after a correct MIC.
- Fix (HAL `wpa.rs`): `same_security` compares the parsed fields (version, group, pairwise, AKMs, capabilities, group management cipher) and skips the PMKID list, as wpa_supplicant's `wpa_compare_rsn_ie`; a changed suite / capability / cut element is still `RsnMismatch` (tests `pmkid_list_is_not_compared`, `message_3_with_the_beacon_element_is_taken`). `Bcm4334::connect` now `disassociate`s (`WLC_DISASSOC` 52, reason 3) after any failed join: the half-open association was what made the next tries time out.
- Diagnostics kept: `GET /api/wifi` (scans, target, each BSS's elements as seen per frame kind, the last mismatch's expected / message 3 elements), UART `wifi seen …` / `wifi joining …` lines. HAL tests don't build for the host as a crate (its panic handler): compile `crypto.rs` + `wpa.rs` in a scratch lib with `rustc --edition 2024 --test`.
- Board: 6 restarts in a row, each joined on the first scan (ch 9, 22–37 s to HTTP up), 0 mismatches. uart_boot (same supplicant) rebuilt and flashed to the boot partition (`fastboot flash boot`, partition `boot`, device `SMDKEXYNOS-`): 7 boots polled every second, each with uart_boot on WiFi at 3–9 s and ferrite up at 13–20 s, 0 mismatches; that uart_boot also has the 2026-11-13 autoboot fix (polling no longer holds it).

Display lists (`dl.rs`): with `dl::ENABLED` (sim `FERRITE_SIM_DL=1`, exynos `POST /api/dl?on=1`, `golden.py --dl`) `render::draw_body` draws through `ObjPool::render.dl_cache`, keyed by `render::dl_key` (a hash of everything `draw_widget_body` reads: anything new it reads must go into the key). A look is recorded on its second sighting against the whole screen, then replayed per clip rect (`List::replay_clipped`). `dl::VERIFY` (sim `FERRITE_SIM_DL_VERIFY=1`, always with `golden.py --dl`) re-records every hit and panics on a stale list. `on_paint`: the VM's drawing opcodes go through `Vm::draw_op` (`canvas!`: the screen, or `ObjPool::render.paint_rec` while `painting`); with display lists `Vm::run_paint` records each widget's `on_paint` (`record_paint`), replays it where it was drawing and keeps it in `render.paints`. - Display list encoding (`dl.rs`, 2026-11-13): a `List` is one `Vec<u32>` stream, like the VM's bytecode but word-aligned and without varints: a header word (opcode bits 0-7, a small argument bits 8-15, usually the colour bits 16-31), 16-bit arguments two to a word, `i32`s a word each, slice data (pixels, coverage, points) inline, zero-padded to a word and read in place (`Offset` is `repr(C)`). Layouts in `dl::code`; `List::ops` decodes into the borrowing `Op<'_>` (replay, dumps, tests); `List::len` = calls. Recording writes each call with one capacity check (`List::call`/`put_bytes`). Was a fixed-size `Op` enum (28 B a call on the board, 32 on the PC). Test `dl::tests::every_call_decodes_to_what_was_recorded`; golden 13/13 default and `--dl`, `--play` identical to `--plain`. Board, play mode (`perf/merge/dl-words-*.json`): Monitor stress 12.8 → 5.4 KB a frame (same ~455 calls), CPU2 job unchanged, CPU0 render 32.1 → 33.1 ms/s (+3%, likely code layout: normal mode moved too); idle tablet home 165 → 146 KB (pixels dominate), CPU0 unchanged.

- VM drawing as lists (step 3d): with a render context (`render::records`: here or away) the VM never draws on the screen. Its drawing builtins outside `on_paint` record into `RenderState::screen_rec` (`canvas!` → `ObjPool::screen_rec`, started on first use), and `on_paint` is recorded in the render phase before the render is handed over (`Vm::record_paint(.., direct = false)`, one list per widget; a pass whose last render still runs leaves the dirty bits for the next). Both queue as `view::Draw` (`Screen(list)` / `Paint(id, list)`, in order; `close_screen_rec` before a paint recording and at the sync) in `RenderState::draws`, handed over by `sync_view` (`needs_sync` counts them). `render::run_job` replays them: screen lists, then each `on_paint` list into the board renderer's capture if it takes it (`capture_list`: `capture_begin`, scissor on the box, replay), the render, then the other `on_paint` lists on the screen (+ `screen_touched`); all kept in `render.paints` (dumps). Lists hold pixels, not references (glyphs, images), so they are recorded on CPU0 from the VM's fonts/images. Without a render context (tests, sim `FERRITE_SIM_ONE_CTX=1`) the old path runs: `capture_paint`, `run_paint` on the screen after the render. Recorded `on_paint` drawing doesn't `screen_touched` (its replay does, after the render, as before). Tests `renderer::tests::the_render_job_replays_the_vms_drawing_around_the_render`, `vm::tests::direct_drawing_is_recorded_for_the_render_side`; golden (sim records) unchanged in all modes.
